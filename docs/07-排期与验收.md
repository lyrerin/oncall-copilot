# 07 · 完整排期与验收

> 12 周，每周一个**可演示的增量**。核心理念：**任何一个周末停下来，项目都是能跑能讲的完整东西**，而不是"半成品等下周接上"。
> 这是防烂尾的唯一有效策略。

---

> "我把工具拆成 4 个独立进程，因为 executor 有写权限而其他三个只读 —— 这是进程级权限隔离，比函数里 if 判断可信。而且我给每个工具都加了硬约束：动作白名单、幂等键短路、高危动作强绑审批号，全部在 server 侧实现，不依赖 prompt。"

| 坑 | 现象 | 解法 |

### W7 · 人在环审批（预计 14~17 小时）

**目标**：`interrupt()` 暂停等人批，审批接口 resume，审批台 v1 能点按钮。

| 天 | 任务 | 产出 |
|---|---|---|
| D1 | `propose_action`：规则匹配 runbook 优先，未命中才问 LLM | `nodes/action.py` |
| D2 | 6 条 runbook 种子数据 | 迁移 or seed 脚本 |
| D3 | `request_approval` 节点 + `interrupt()` + 幂等 upsert 审批记录 | 同上 |
| D4 | `route_after_approval` + `execute_action` 占位版 | 同上 |
| D5 | `approvals.py` API：`/pending` + `/approve` | `api/approvals.py` |
| D6 | Streamlit 待审批页面 | `ui/approval_console.py` |
| D7 | **重启进程后审批**实验 + 缓冲 | 记录 |

**本周验收**
- [ ] 图停在 `request_approval`，`__interrupt__` 载荷含 plan_id / action / risk_level
- [ ] `approvals` 表有一行 `decision IS NULL`
- [ ] 审批台待审批页显示卡片，含根因、置信度、证据摘要、参数 JSON
- [ ] 点"批准"，图从 `interrupt` 处继续，走到 `execute_action`
- [ ] 点"驳回"，图走 `escalate`，不执行
- [ ] **重复点批准第二次返回 409**
- [ ] **`interrupt()` 前的副作用不会重复执行**（审批记录只有一行，不是两行）

**本周新学**（本周的坑最多，逐个踩一遍）
| 技术/坑 | 说明 |
|---|---|
| **`interrupt()` 所在节点 resume 时整体重跑** | `interrupt()` 之前的代码会执行两次。**副作用必须放在 interrupt 之后，或者做成幂等 upsert。** 我最初把建审批记录写在 interrupt 前，发现 resume 时插了两行。 |
| `Command(resume=...)` | resume 的入参就是 `interrupt()` 的返回值，一一对应 |
| thread_id 必须稳定 | resume 用不同的 thread_id 会找不到 checkpoint，报图状态不存在 |
| 中断载荷的序列化 | 只能放 JSON 可序列化的东西，datetime 要转字符串 |

**面试讲点**
> "HITL 有个反直觉的地方：`interrupt()` 所在节点在 resume 时会从头重新执行。所以 `interrupt()` 之前的任何副作用都会被做两次。我把创建审批记录改成了幂等 upsert —— 先查有没有，有就复位状态而不是新插一行。这个坑不看文档根本想不到。"

## 4. 演示脚本与四个杀手锏

### 4.1 8 分钟演示流程

| 时间 | 动作 | 说的话 |
|---|---|---|
| 0:00-0:30 | 打开架构图（README 里的 mermaid） | "告警进来，Agent 自动查 4 个系统的证据，高危操作人工审批后执行。" |
| 0:30-1:30 | `python -m mockenv.alertgen --once`，切到审批台时间线页 | "现在灌一条真告警，看 Agent 怎么推的。" |
| 1:30-3:00 | 时间线页出现证据卡片，逐条解释 | "先查变更 —— 这是成本最低命中率最高的动作。然后看错误模板聚类。再验证指标是否真异常。" |
| 3:00-4:00 | 根因和置信度出现 | "根因是内存泄漏，置信度 0.82，高于 0.6 阈值所以进入处置。" |
| 4:00-5:00 | 切待审批页，点批准 | **杀手锏 1**：审批卡片上有证据链和回滚计划 |
| 5:00-6:00 | 状态变 resolved，看审计页 | **杀手锏 2**：完整审计链 agent → human → agent |
| 6:00-7:00 | 重复点批准 → 409 | **杀手锏 3**：主动展示幂等拒绝 |
| 7:00-8:00 | `docker compose restart worker`，再审批一次，成功执行 | **杀手锏 4**：进程重启后 resume，证明状态在 Postgres 不在内存 |

### 4.2 四个杀手锏（必须准备）

| # | 演示 | 证明什么 | 面试官反应 |
|---|---|---|---|
| 1 | 审批卡片带完整上下文 | 人在环不是走过场，审批人真能判断 | "想得挺细" |
| 2 | 审计流水完整 | AI 操作系统必须有可追溯性 | "有生产意识" |
| 3 | 重复审批被拒 | 幂等不是嘴上说的 | "这个细节做对了" |
| 4 | 重启进程后 resume | checkpointer 的必要性 | **"这个我没想到"** |

**杀手锏 4 是决胜局。** 绝大多数候选人的 Agent 项目跑完就结束，讲不出"状态在哪、重启会怎样"。准备一个 30 秒的版本随时能演示。
