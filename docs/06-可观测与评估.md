# 06 · 可观测与评估

> 这一章决定你的项目是"我做了个 Agent"还是"我做了个**可衡量**的 Agent"。
> AI 应用开发岗面试到最后一定问：**"效果怎么样？成本多少？慢在哪？"**

---

## 0. 三层观测的分工

很多人把"可观测"理解成"接个 Langfuse"。不够。三层缺一不可：

| 层 | 回答什么问题 | 用什么 | 落在哪 |
|---|---|---|---|
| **链路追踪** | 这一次诊断每步耗时多少、烧了多少 token | Langfuse + LangChain callback | Langfuse 面板 |
| **业务指标** | 自动恢复率、转人工率、MTTR、单次成本 | 业务表聚合 | `/incidents/metrics` + Streamlit 看板 |
| **质量评估** | 根因判对了没、动作选对了没 | 评估集回放 | `eval_runs` 表 + 报告 |

**面试话术**：*"我做的是三层观测：链路层用 Langfuse 看单次诊断的内部开销，业务层把 token 和成本写进 incidents 表做聚合，质量层用 5 个场景的评估集回放，记录根因准确率和成本。三层分别回答'慢在哪''值不值''准不准'。"*

## 1. Langfuse 接入

```python
# app/obs/tracing.py
"""Langfuse 追踪封装。

设计原则：观测失败绝不影响业务。所有 Langfuse 调用都包 try/except。
"""
import logging
import os
from contextlib import contextmanager

from app.config import settings

log = logging.getLogger(__name__)

_enabled = False


def init_langfuse() -> None:
    """在 lifespan / worker startup 里调用一次。

    Langfuse SDK 通过环境变量读取凭据，所以这里设置 os.environ
    而不是把 key 传进 CallbackHandler —— SDK 内部就是这么设计的。
    """
    global _enabled
    if not settings.langfuse_enabled:
        log.info("langfuse disabled")
        return
    if not settings.langfuse_public_key or not settings.langfuse_secret_key:
        log.warning("langfuse enabled but keys missing; falling back to disabled")
        return

    os.environ["LANGFUSE_PUBLIC_KEY"] = settings.langfuse_public_key
    os.environ["LANGFUSE_SECRET_KEY"] = settings.langfuse_secret_key
    os.environ["LANGFUSE_HOST"] = settings.langfuse_host
    _enabled = True
    log.info("langfuse enabled -> %s", settings.langfuse_host)


def build_run_config(thread_id: str, incident_id: int, *, phase: str) -> dict:
    """构造 ainvoke 的 config。

    configurable.thread_id 是 LangGraph 用来定位 checkpoint 的键 ——
    必须和业务关联起来，否则 Langfuse 里的 trace 和数据库里的 incident 对不上。
    """
    config: dict = {
        "configurable": {"thread_id": thread_id},
        "metadata": {
            "incident_id": incident_id,
            "thread_id": thread_id,
            "phase": phase,
            "prompt_version": _prompt_version(),
        },
        "run_name": f"diagnosis:{incident_id}:{phase}",
        "tags": ["oncall-copilot", phase],
    }

    handler = get_callback_handler()
    if handler is not None:
        config["callbacks"] = [handler]
    return config


def get_callback_handler():
    """构造 LangChain 回调。

    版本差异提醒：langfuse v2 是 `from langfuse.callback import CallbackHandler`，
    v3 是 `from langfuse.langchain import CallbackHandler`。
    锁死版本后按你装的那版写；两版都 import 失败就降级为不追踪。
    """
    if not _enabled:
        return None
    try:
        from langfuse.langchain import CallbackHandler   # v3
    except ImportError:
        try:
            from langfuse.callback import CallbackHandler  # v2
        except ImportError:
            log.warning("langfuse CallbackHandler not importable; tracing disabled")
            return None
    try:
        return CallbackHandler()
    except Exception as e:                            # noqa: BLE001
        log.warning("failed to build langfuse handler: %s", e)
        return None


def _prompt_version() -> str:
    from app.agent.prompts import PROMPT_VERSION
    return PROMPT_VERSION


def flush() -> None:
    """worker 任务结束时 flush，否则短命进程会丢 trace。"""
    if not _enabled:
        return
    try:
        from langfuse import Langfuse
        Langfuse().flush()
    except Exception:                                 # noqa: BLE001
        pass


@contextmanager
def span(name: str, **metadata):
    """手动埋点的轻量封装。用于 MCP 工具调用这种不走 LangChain 的操作。"""
    if not _enabled:
        yield None
        return
    try:
        from langfuse import Langfuse
        client = Langfuse()
        s = client.start_span(name=name, metadata=metadata)
        try:
            yield s
        finally:
            s.end()
    except Exception:                                 # noqa: BLE001
        yield None
```

### 在节点里补 token 统计

Langfuse 能自动抓到 LLM 调用的 token，但**图状态里的 `usage` 需要自己填**。最干净的做法是给 LLM 加一个统计回调：

```python
# app/obs/usage.py
"""把 LLM 的 token 用量回填进图状态。

问题：LangChain 的 usage_metadata 在 AIMessage 上，
     但 structured output 走的是 function calling，
     节点里拿到的是 pydantic 对象，看不到 token 数。

解法：用回调把每次调用的 token 记到一个 contextvar，
     节点结束时读出来写进 state["usage"]。
"""
from contextvars import ContextVar

from langchain_core.callbacks import BaseCallbackHandler

_usage: ContextVar[dict] = ContextVar("llm_usage", default=None)


def reset_usage() -> None:
    _usage.set({"prompt_tokens": 0, "completion_tokens": 0, "llm_calls": 0})


def current_usage() -> dict:
    return _usage.get() or {"prompt_tokens": 0, "completion_tokens": 0, "llm_calls": 0}


class UsageCallback(BaseCallbackHandler):
    """挂在 config["callbacks"] 上，自动累计 token。"""

    def on_llm_end(self, response, **kwargs) -> None:  # noqa: ANN001
        acc = _usage.get()
        if acc is None:
            return
        try:
            msg = response.generations[0][0].message
            meta = getattr(msg, "usage_metadata", None) or {}
            acc["prompt_tokens"] += int(meta.get("input_tokens", 0))
            acc["completion_tokens"] += int(meta.get("output_tokens", 0))
            acc["llm_calls"] += 1
            _usage.set(acc)
        except Exception:                              # noqa: BLE001
            pass
```

然后在 `build_run_config` 里把 `UsageCallback()` 一起挂上，每个节点的 `usage` 返回 `current_usage()` 的增量。

**为什么要用 `contextvars` 而不是全局变量**：worker 是并发的（`max_jobs=5`），全局变量会让 5 个诊断的 token 互相污染。**`contextvars` 是 asyncio 下的正确选择** —— 这个细节面试问"并发下你怎么统计"时能答。

## 2. 业务指标

### 2.1 指标定义（写进 README，面试照着念）

| 指标 | 计算方式 | 目标 | 说明 |
|---|---|---|---|
| **自动恢复率** | `resolved / total` | > 60% | 不需要人工介入就解决的比例 |
| **转人工率** | `escalated / total` | 记录即可 | 太高说明能力不足，太低可能是乱处置 |
| **审批驳回率** | `rejected / (approved + rejected)` | < 20% | **高说明处置方案质量差或阈值太松** |
| **审批超时率** | `timeout / total_approvals` | < 10% | 高说明通知没送达或审批台难用 |
| **平均 MTTR** | `avg(mttr_seconds)` | 越低越好 | 要和"人工处理基线"对比才有意义 |
| **单次诊断成本** | `avg(total_cost_usd)` | 记录 | 拆成"到审批前"和"审批后"两段 |
| **平均调查轮次** | `avg(diagnosis_rounds)` | ≈ 1.5 | > 2 说明首轮调查质量差 |
| **根因准确率** | 见 §3 | > 80% | **唯一需要评估集才能算的指标** |

### 2.2 指标接口

```python
# app/api/metrics.py
from datetime import datetime, timedelta, timezone

from fastapi import APIRouter, Depends, Query
from sqlalchemy import case, func, select
from sqlalchemy.ext.asyncio import AsyncSession

from app.db.base import get_session
from app.db.models import ActionPlan, Approval, Execution, Incident

router = APIRouter()


@router.get("/metrics/summary")
async def metrics_summary(
    days: int = Query(default=7, ge=1, le=90),
    s: AsyncSession = Depends(get_session),
) -> dict:
    """运营指标汇总。给 Streamlit 看板和面试演示用。"""
    since = datetime.now(timezone.utc) - timedelta(days=days)

    inc = (await s.execute(
        select(
            func.count().label("total"),
            func.sum(case((Incident.status == "resolved", 1), else_=0)).label("resolved"),
            func.sum(case((Incident.status == "escalated", 1), else_=0)).label("escalated"),
            func.avg(Incident.mttr_seconds).label("avg_mttr"),
            func.avg(Incident.confidence).label("avg_confidence"),
            func.avg(Incident.diagnosis_rounds).label("avg_rounds"),
            func.sum(Incident.total_tokens).label("total_tokens"),
            func.sum(Incident.total_cost_usd).label("total_cost"),
            func.avg(Incident.total_cost_usd).label("avg_cost"),
        ).where(Incident.detected_at >= since)
    )).one()

    total = inc.total or 0
    appr = (await s.execute(
        select(
            func.sum(case((Approval.decision == "approved", 1), else_=0)).label("approved"),
            func.sum(case((Approval.decision == "rejected", 1), else_=0)).label("rejected"),
            func.sum(case((Approval.decision == "timeout", 1), else_=0)).label("timeout"),
            func.count().label("all_decided"),
        ).where(Approval.requested_at >= since)
    )).one()

    execs = (await s.execute(
        select(
            func.count().label("total"),
            func.sum(case((Execution.status == "succeeded", 1), else_=0)).label("succeeded"),
            func.avg(Execution.duration_ms).label("avg_duration_ms"),
        ).where(Execution.started_at >= since)
    )).one()

    decided = (appr.approved or 0) + (appr.rejected or 0) + (appr.timeout or 0)
    return {
        "window_days": days,
        "incidents": {
            "total": total,
            "resolved": inc.resolved or 0,
            "escalated": inc.escalated or 0,
            "auto_resolve_rate": round((inc.resolved or 0) / total, 4) if total else 0,
            "escalate_rate": round((inc.escalated or 0) / total, 4) if total else 0,
            "avg_mttr_seconds": round(float(inc.avg_mttr or 0), 1),
            "avg_confidence": round(float(inc.avg_confidence or 0), 3),
            "avg_investigation_rounds": round(float(inc.avg_rounds or 0), 2),
        },
        "cost": {
            "total_tokens": int(inc.total_tokens or 0),
            "total_usd": round(float(inc.total_cost or 0), 4),
            "avg_usd_per_incident": round(float(inc.avg_cost or 0), 6),
        },
        "approvals": {
            "decided": decided,
            "approved": appr.approved or 0,
            "rejected": appr.rejected or 0,
            "timeout": appr.timeout or 0,
            "reject_rate": round((appr.rejected or 0) / decided, 4) if decided else 0,
            "timeout_rate": round((appr.timeout or 0) / decided, 4) if decided else 0,
        },
        "executions": {
            "total": execs.total or 0,
            "succeeded": execs.succeeded or 0,
            "success_rate": round((execs.succeeded or 0) / (execs.total or 1), 4),
            "avg_duration_ms": int(execs.avg_duration_ms or 0),
        },
    }


@router.get("/metrics/nodes")
async def metrics_by_tool(
    days: int = Query(default=7, ge=1, le=90),
    s: AsyncSession = Depends(get_session),
) -> dict:
    """按 MCP 工具统计调用次数和耗时 —— 回答"慢在哪"。

    这是优化延迟的起点：哪个工具最慢、哪个失败率最高，一目了然。
    """
    from app.db.models import Evidence
    since = datetime.now(timezone.utc) - timedelta(days=days)
    rows = (await s.execute(
        select(
            Evidence.tool_name,
            func.count().label("calls"),
            func.sum(case((Evidence.ok.is_(True), 1), else_=0)).label("ok_calls"),
            func.avg(Evidence.duration_ms).label("avg_ms"),
            func.max(Evidence.duration_ms).label("max_ms"),
        )
        .where(Evidence.collected_at >= since)
        .group_by(Evidence.tool_name)
        .order_by(func.count().desc())
    )).all()

    return {
        "tools": [
            {
                "tool": r.tool_name, "calls": r.calls,
                "success_rate": round((r.ok_calls or 0) / r.calls, 4),
                "avg_ms": int(r.avg_ms or 0), "max_ms": r.max_ms,
            }
            for r in rows
        ]
    }
```

> **`metrics_by_tool` 是"慢在哪"的答案**。面试演示时打开它，指出"`top_error_patterns` 平均 800ms 是瓶颈，因为它在 2000 条日志上做正则聚类" —— 这说明你真的**测过**，而不是"感觉挺快的"。

## 3. 评估体系（最容易被忽略，也最有区分度）

### 3.1 评估集

```yaml
# eval/cases.yaml
# 每个场景对应 mockenv.generate 里的 SCENARIOS，
# 因为生成数据时就已经确定了"正确答案"。
#
# ground truth 三件套：
#   expected_tags    → 根因标签（模糊匹配，容忍措辞差异）
#   expected_service → 受影响服务
#   expected_action  → 期望的动作（可空，表示"只要有合理处置即可"）

- name: memory_leak_order_service
  scenario: memory_leak
  expected_service: order-service
  expected_tags: [memory_leak]
  expected_action: restart_deployment
  difficulty: normal
  notes: JVM 堆内存泄漏，变更引入了缓存层未设上限

- name: bad_release_api_gateway
  scenario: bad_release
  expected_service: api-gateway
  expected_tags: [bad_release]
  expected_action: rollback_deployment
  difficulty: normal
  notes: 路由中间件重构导致 panic

- name: db_deadlock_order_db
  scenario: db_deadlock
  expected_service: order-db
  expected_tags: [db_deadlock]
  expected_action: restart_deployment
  difficulty: hard
  notes: max_connections 被调小导致连接池耗尽

- name: cpu_saturation_user_service
  scenario: cpu_saturation
  expected_service: user-service
  expected_tags: [cpu_saturation]
  expected_action: scale_deployment
  difficulty: hard
  notes: 缩容导致 CPU 打满，变更类型是 scale 不是 deploy

- name: cache_miss_storm_redis
  scenario: cache_miss_storm
  expected_service: redis-cache
  expected_tags: [cache_miss_storm]
  expected_action: restart_deployment
  difficulty: hard
  notes: maxmemory 调小引发缓存雪崩，日志在 redis 侧但根因影响 order-service
```

**为什么用 `expected_tags` 而不是字符串比对**：模型的根因表述永远不一样（"JVM 堆内存泄漏" vs "内存持续增长导致 GC 频繁"）。字符串精确匹配的准确率恒为 0。**按标签集合匹配才是可用的评估**：

```python
def tag_correct(predicted: list[str], expected: list[str]) -> bool:
    """标签有交集即算对。宽松但可用。"""
    return bool(set(predicted or []) & set(expected or []))
```

> 面试点：*"我第一版评估用字符串精确匹配，准确率永远是 0 —— 因为模型每次措辞都不同。改成根因标签集合匹配后才有意义。这件事教会我：评估指标设计本身比跑评估更难。"*

### 3.2 评估执行器

```python
# eval/run_eval.py
"""评估执行器。

用法：
    python -m eval.run_eval                    # 跑全部案例
    python -m eval.run_eval --case memory_leak_order_service
    python -m eval.run_eval --no-execute       # 只到 propose_action，不真执行（快、省钱）

设计要点：
  1. 每次跑用独立的 incident + thread_id，互不干扰
  2. --no-execute 模式把图跑到 awaiting_approval 就停，
     不经过 HITL（评估的是"判断能力"，不是"审批流程"）
  3. 结果写进 eval_runs 表，可以横向对比不同 prompt/model 版本
"""
import argparse
import asyncio
import json
import subprocess
import time
from datetime import datetime, timezone

import httpx
import yaml
from sqlalchemy import select, text

from app.agent.mcp_client import init_mcp_tools
from app.agent.runner import run_diagnosis, resume_diagnosis
from app.config import settings
from app.db.base import SessionLocal
from app.db.models import EvalRun
from mockenv.generate import SCENARIOS, seed_scenario
from mockenv.alertgen import build_alertmanager_payload

API = "http://api:8000"


def _git_sha() -> str:
    try:
        return subprocess.check_output(
            ["git", "rev-parse", "--short", "HEAD"], text=True
        ).strip()
    except Exception:                                 # noqa: BLE001
        return "unknown"


async def run_case(case: dict, *, execute: bool) -> dict:
    """跑单个案例，返回结构化结果。"""
    scenario = case["scenario"]
    name = case["name"]

    # 1) 重新灌该场景的数据（保证环境一致）
    await seed_scenario(scenario, minutes=60)

    # 2) 造一条唯一告警（加时间戳避免被 Redis 去重吃掉）
    payload = build_alertmanager_payload(scenario)
    payload["groupKey"] = f"eval-{name}-{int(time.time())}"
    payload["alerts"][0]["fingerprint"] = f"eval-{name}-{int(time.time())}"
    payload["alerts"][0]["startsAt"] = datetime.now(timezone.utc).isoformat()

    started = time.perf_counter()
    async with httpx.AsyncClient(timeout=60) as client:
        r = await client.post(f"{API}/webhook/alertmanager", json=payload)
        r.raise_for_status()
        body = r.json()
    incident_id = body["incident_id"]
    thread_id = body["thread_id"]

    # 3) 等诊断跑到 awaiting_approval（或终态）
    result = await _wait_for_state(incident_id, timeout=180)

    # 4) 需要的话批准执行（评估处置能力）
    if execute and result["status"] == "awaiting_approval":
        async with httpx.AsyncClient(timeout=60) as client:
            await client.post(
                f"{API}/incidents/{incident_id}/approve",
                json={"decision": "approved", "approver": "eval-bot",
                      "comment": "automated evaluation"},
            )
        result = await _wait_for_state(incident_id, timeout=180)

    latency_ms = int((time.perf_counter() - started) * 1000)

    # 5) 判定
    async with SessionLocal() as s:
        row = (await s.execute(text("""
            SELECT i.service, i.root_cause, i.confidence, i.status,
                   i.total_tokens, i.total_cost_usd, i.mttr_seconds,
                   (SELECT array_agg(DISTINCT h.rationale) FROM hypotheses h
                     WHERE h.incident_id = i.id AND h.adopted) AS rationales,
                   (SELECT p.action FROM action_plans p
                     WHERE p.incident_id = i.id ORDER BY p.id LIMIT 1) AS action
            FROM incidents i WHERE i.id = :iid
        """), {"iid": incident_id})).one()

        # 从证据里反推模型给出的 tags（tags 没落库，用 hypotheses 的标签代替）
        tags = _extract_tags_from_db(await _fetch_tags(s, incident_id))

    service_ok = (row.service or "") == case["expected_service"]
    tags_ok = bool(set(tags) & set(case["expected_tags"]))
    action_ok = (
        case.get("expected_action") is None or row.action == case["expected_action"]
    )

    return {
        "case": name,
        "scenario": scenario,
        "incident_id": incident_id,
        "difficulty": case.get("difficulty", "normal"),
        "predicted_service": row.service,
        "expected_service": case["expected_service"],
        "service_correct": service_ok,
        "predicted_tags": tags,
        "expected_tags": case["expected_tags"],
        "tags_correct": tags_ok,
        "predicted_action": row.action,
        "expected_action": case.get("expected_action"),
        "action_correct": action_ok,
        "confidence": row.confidence,
        "final_status": row.status,
        "latency_ms": latency_ms,
        "tokens": row.total_tokens,
        "cost_usd": float(row.total_cost_usd or 0),
        "mttr_seconds": row.mttr_seconds,
        "root_cause_text": row.root_cause,
    }


async def _fetch_tags(s, incident_id: int) -> list[str]:
    """根因标签目前没单独落库，用证据摘要里的关键词做粗提取。

    改进方向（写进 README 的 TODO）：
      给 hypotheses 表加 tags JSONB 字段，直接存模型的 tags。
      这是第一版就该做但可以后补的事。
    """
    rows = (await s.execute(text("""
        SELECT h.rationale, h.statement FROM hypotheses h
        WHERE h.incident_id = :iid AND h.adopted
    """), {"iid": incident_id})).all()
    blob = " ".join(f"{r.statement or ''} {r.rationale or ''}" for r in rows).lower()
    found = []
    for tag in ("memory_leak", "bad_release", "db_deadlock", "cpu_saturation",
                "cache_miss_storm", "network_issue", "config_error"):
        keywords = tag.replace("_", " ").split()
        if all(k in blob for k in keywords) or tag.replace("_", "") in blob.replace("_", ""):
            found.append(tag)
    return found


async def _wait_for_state(incident_id: int, *, timeout: int = 180) -> dict:
    """轮询直到 incident 进入终态或待审批。"""
    terminal = {"resolved", "escalated", "failed", "awaiting_approval"}
    deadline = time.time() + timeout
    async with httpx.AsyncClient(timeout=30) as client:
        while time.time() < deadline:
            r = await client.get(f"{API}/incidents/{incident_id}")
            inc = r.json()["incident"]
            if inc["status"] in terminal:
                return inc
            await asyncio.sleep(3)
    return {"status": "timeout"}


async def main() -> None:
    ap = argparse.ArgumentParser()
    ap.add_argument("--cases", default="eval/cases.yaml")
    ap.add_argument("--case", default=None, help="只跑单个案例")
    ap.add_argument("--no-execute", action="store_true",
                    help="跳过审批执行，只评估判断能力（更快更省）")
    ap.add_argument("--label", default="", help="本次运行的标签，便于对比")
    args = ap.parse_args()

    await init_mcp_tools()

    cases = yaml.safe_load(open(args.cases, encoding="utf-8"))
    if args.case:
        cases = [c for c in cases if c["name"] == args.case]
    if not cases:
        print("no cases matched")
        return

    results = []
    for c in cases:
        print(f"\n=== {c['name']} ===")
        try:
            res = await run_case(c, execute=not args.no_execute)
        except Exception as e:                        # noqa: BLE001
            print(f"  ERROR: {type(e).__name__}: {e}")
            res = {"case": c["name"], "error": str(e), "service_correct": False,
                   "tags_correct": False, "action_correct": False,
                   "tokens": 0, "cost_usd": 0.0, "latency_ms": 0}
        results.append(res)
        print(f"  服务: {res.get('predicted_service')} "
              f"{'✅' if res['service_correct'] else '❌'}")
        print(f"  标签: {res.get('predicted_tags')} "
              f"{'✅' if res['tags_correct'] else '❌'} (期望 {c['expected_tags']})")
        print(f"  动作: {res.get('predicted_action')} "
              f"{'✅' if res['action_correct'] else '❌'}")
        print(f"  成本: ${res['cost_usd']:.4f}  耗时: {res['latency_ms']}ms")

    # ---- 汇总 ----
    n = len(results)
    ok_service = sum(r.get("service_correct", False) for r in results)
    ok_tags = sum(r.get("tags_correct", False) for r in results)
    ok_action = sum(r.get("action_correct", False) for r in results)
    summary = {
        "total": n,
        "service_accuracy": round(ok_service / n, 4),
        "root_cause_accuracy": round(ok_tags / n, 4),
        "action_accuracy": round(ok_action / n, 4),
        "avg_latency_ms": int(sum(r.get("latency_ms", 0) for r in results) / n),
        "avg_tokens": int(sum(r.get("tokens", 0) for r in results) / n),
        "avg_cost_usd": round(sum(r.get("cost_usd", 0.0) for r in results) / n, 6),
    }

    print("\n" + "=" * 60)
    print(json.dumps(summary, ensure_ascii=False, indent=2))
    print("=" * 60)

    # ---- 落库 ----
    async with SessionLocal() as s:
        s.add(EvalRun(
            finished_at=datetime.now(timezone.utc),
            git_sha=_git_sha(), model=settings.llm_model,
            prompt_version=_prompt_version(),
            total=n, service_correct=ok_service,
            root_cause_correct=ok_tags, action_correct=ok_action,
            avg_latency_ms=summary["avg_latency_ms"],
            avg_prompt_tokens=summary["avg_tokens"],
            total_cost_usd=summary["avg_cost_usd"] * n,
            detail=results,
        ))
        await s.commit()

    print(f"\nrun saved. label={args.label}")


def _prompt_version() -> str:
    from app.agent.prompts import PROMPT_VERSION
    return PROMPT_VERSION


if __name__ == "__main__":
    asyncio.run(main())
```

### 3.3 评估的三个陷阱（面试高级话题）

| 陷阱 | 表现 | 解法 |
|---|---|---|
| **评估泄漏** | 准确率虚高到 100% | mock 告警的 `scenario` 字段在 `ingest` 处剥离；**验证方法：把模型换成随机猜测，准确率应该掉到 20%** |
| **字符串比对** | 准确率恒为 0 | 用根因标签集合匹配，不用文本相似度 |
| **单次运行的偶然性** | 5 个案例跑一次，准确率 80%，但可能是运气 | 每个案例跑 3 次取多数（`--repeat 3`）；**LLM 有随机性，点估计不可信** |

**第三个陷阱的加法**：

```python
# 在 main() 里加个 --repeat
results = []
for c in cases:
    runs = [await run_case(c, execute=not args.no_execute) for _ in range(args.repeat)]
    # 多数投票
    tags_votes = Counter(tuple(sorted(r["predicted_tags"])) for r in runs)
    majority = tags_votes.most_common(1)[0][0]
    ...
```

> 面试话术：*"我给每个案例跑 3 次做多数投票。因为 LLM 输出有随机性，单次结果可能就是运气好。报告里我给的是 3 次的多数结果和标准差，不是单次点估计。"* ——这句话直接把你和"跑了一遍就说准确率 90%"的候选人区分开。

## 4. 成本与延迟优化（可量化的优化故事）

这一节是面试的高价值区：**"你怎么优化的"比"你做了什么"更重要**。

### 4.1 三个优化动作与量化结果

| 优化 | 做法 | 量化（填你实测的数） |
|---|---|---|
| **并行证据采集** | `Send` fan-out 替代串行 | 端到端从 `4×2s=8s` 降到 `max(2s)=2s`；**采集阶段耗时降 75%** |
| **规则优先于 LLM** | runbook 按 tags 精确匹配命中时不调 LLM | `propose_action` 的 LLM 调用从 100% 降到 30%（6 条 runbook 覆盖大部分场景）；**该节点 token 降 100%（命中时 0 调用）** |
| **小模型分流** | `triage` / `propose_action` 用 cheap 模型 | 这两处占总调用数的 40%，单价按 1/3 算，**总成本降约 25%** |

**必须真测，不要编数**。写一个对比脚本：

```python
# eval/ab_test.py
"""A/B 对比：串行 vs 并行、大模型 vs 小模型。

用法：
    python -m eval.ab_test --config baseline
    python -m eval.ab_test --config parallel
然后对比 eval_runs 表里两次运行的成本和延迟。
"""
```

### 4.2 成本优化的四个"闸门"（都在配置里）

```python
max_investigation_rounds: int = 3      # 调查回环上限
max_evidence_per_round: int = 6        # 单轮并行分支上限
confidence_threshold: float = 0.6      # 低于它才回环
# 工具侧截断
message[:500]                          # 日志行截断
payload 上限 20000 字符                # 证据截断
points 抽样到 60 个点                  # 指标降采样
```

**面试话术**：*"Agent 的成本控制不能只靠 prompt 里写'请节约'。我在四个位置设了硬闸门：回环轮次、单轮分支数、工具返回截断、指标降采样。全部在代码里，模型绕不过去。"*

### 4.3 延迟分解（要有数）

```python
# 在 report 节点里记录各阶段耗时
stage_timing = {
    "ingest_ms": ...,
    "triage_ms": ...,
    "investigation_ms": ...,     # 并行，等于最慢分支
    "synthesize_ms": ...,
    "approval_wait_ms": ...,     # 人在环等待时间（要单独统计！）
    "execute_ms": ...,
    "verify_ms": ...,
}
```

> **`approval_wait_ms` 必须和 agent 自身耗时分开统计**。否则 MTTR 里混进了"值班人睡了 20 分钟"，让 Agent 的延迟优化效果被淹没。**这个区分能力本身就是加分项** —— 面试官能看出你分得清"系统慢"和"流程慢"。

## 5. 告警与看板

### 5.1 关键告警规则（自监控）

系统自己也要被监控：

| 规则 | 阈值 | 含义 |
|---|---|---|
| 诊断失败率 | 5 分钟内 > 30% | MCP server 挂了或 LLM 不可用 |
| 审批积压 | > 5 条待审批 | 值班人掉线或通知失效 |
| 单次诊断成本 | > $0.05 | prompt 泄漏或回环失控 |
| checkpointer 写入延迟 | p99 > 500ms | Postgres 压力大 |
| MCP 工具失败率 | 单工具 > 10% | 某个 mock server 有问题 |

### 5.2 Streamlit 看板补充页

在审批台加第四个页面，直接读 `/metrics/summary` 和 `/metrics/nodes`，画出：
- 自动恢复率 / 转人工率的趋势线（按天）
- 单次成本分布直方图
- 各工具的调用次数和平均耗时柱状图（**"慢在哪"的答案**）
- 置信度 vs 实际正确率的关系图（**校准曲线**，进阶）

**校准曲线是什么**（进阶加分）：把诊断按置信度分桶（0.5-0.6 / 0.6-0.7 / ...），看每个桶里的实际准确率。理想情况是"置信度 0.7 的样本里 70% 是对的"。

> 如果曲线偏离很多（比如置信度 0.9 的样本只有 50% 正确），说明**模型给的置信度不诚实**，`confidence_threshold` 这个路由依据就不可靠 —— 这是可以写进 README "已知问题"的高级发现。**面试时主动说这个，效果极好。**
