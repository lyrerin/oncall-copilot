## A. 项目定位类（开场必问）

### A1. 介绍一下这个项目

**一句话**：一个 AI 值班 Copilot —— 告警进来后自动并行调查多个系统的证据，产出带置信度的根因判断和处置方案，高危操作走人工审批后经 MCP 执行。

**展开（30 秒版）**
> "值班工程师半夜被叫醒，要先翻告警、查日志、查指标、查变更记录，才能判断是不是已知故障。信息散在 5 个系统里，MTTR 很长，新人还不会处理。
>
> 我的系统接收 Prometheus Alertmanager 的告警 webhook，用一个 LangGraph 状态图编排诊断：先用 `Send` 并行采集日志、指标、变更、历史故障四路证据，然后让模型综合出带置信度的根因假设。置信度不够就带着'缺什么信息'回环补调查，最多 3 轮。算出根因后匹配预定义的 runbook 生成处置方案，**高危动作会 `interrupt()` 暂停，等值班人在审批台点批准**，批准后用幂等的方式通过 MCP 执行器真正执行，最后重新拉指标验证是否恢复。
>
> 整个流程状态持久化在 Postgres 里，所以进程重启能从断点续跑，这也是人在环能成立的前提。"

**代码位置**：`app/agent/graph.py`、`app/agent/nodes/`

**加分补充**：主动说出"这个项目的两个核心不是'用了 LangGraph'，而是**状态可持久化**和**执行有安全边界**"。

### A2. 这个项目最难的地方是什么？

**一句话**：把"Agent 判断"和"Agent 能做什么"的边界划清楚。

**展开**
> "难点不在调通 LangGraph，在于三件事：
>
> 一是**置信度必须可编程**。我让模型输出的不是一段根因描述，而是结构化的假设 + 置信度 + 缺什么信息，因为置信度是路由依据 —— 低于阈值回环补调查，高于才敢提处置。自由文本没法做判断。
>
> 二是**高危操作不能靠 prompt 约束**。动作白名单、幂等键、高危动作强绑审批号，全写在 MCP server 侧，模型就算被注入了也绕不过去。
>
> 三是**HITL 有个反直觉的坑**：`interrupt()` 所在节点在 resume 时会从头重跑，所以 interrupt 之前的副作用会执行两次。我最初把创建审批记录写在 interrupt 前，resume 时插了两行，后来改成幂等 upsert。"

**加分补充**：主动说出踩过的具体 bug，比说"架构设计很难"可信十倍。

### A3. 你为什么不做成客服 / 数据分析 Agent？

**一句话**：因为 MCP 在这个场景是刚需，在那个场景是硬凑。

**展开**
> "工具拆成独立 MCP server 的前提是**工具天然属于不同系统、不同团队**。日志系统归 SRE 团队，CMDB 归平台团队，处置执行要单独的写权限 —— 这才是 MCP 的语义：跨团队的工具契约。
>
> 如果是客服 Agent 查自家订单库，直接调后端 API 更合理，上 MCP 就是为了用而用。面试官一追问'你为什么不用普通函数'就答不上来了。"

**加分补充**：这个回答同时展示了"你知道 MCP 解决什么问题"，比"我用了 MCP"高一个层次。

## B. MCP 类

### B1. MCP 是什么？解决了什么问题？

**一句话**：MCP 是把"工具/数据源"和"AI 应用"之间的接口标准化，把 N×M 的集成问题变成 N+M。

**展开**
> "没有 MCP 的时候，每个 AI 应用要给每个工具写一套适配代码，M 个应用对 N 个工具就是 M×N 份。MCP 定义了统一协议，工具方只要实现一次 server，任何 MCP client 都能用。
>
> 协议有三个原语：**tools**（可调用的函数）、**resources**（可读的数据）、**prompts**（预置模板）。我主要用 tools。
>
> 传输方式有 stdio（本地子进程）和 streamable-http（远程服务）。我的 4 个 server 都是独立容器，所以用 streamable-http。"

**代码位置**：`mcp_servers/*.py`、`app/agent/mcp_client.py`

**加分补充**：说出"我加一个新 MCP server，prompt 里的工具目录自动更新，一行 prompt 都不用改" —— 这是真实收益。

---

### B2. 你为什么把工具拆成 4 个独立进程？普通函数不行吗？

**一句话**：权限隔离 + 独立部署 + 跨团队边界 + 可替换，四条理由。

**展开**
| 理由 | 具体体现 |
|---|---|
| **权限隔离** | `mcp-executor` 是唯一有写权限的服务。诊断 Agent 拿到的三个工具全是只读的。**进程级隔离比函数里 if 判断可信** |
| **独立部署扩容** | 日志 server 是 IO 密集连 Loki，指标 server 连时序库，资源画像不同 |
| **跨团队边界** | 现实中这些系统归不同团队，MCP 是"跨团队工具契约" |
| **可替换** | mock 换成真的 Loki / Prometheus，只改 server 内部实现，Agent 一行不动 |

**加分补充**：最后一条直接支撑了你的"半真实数据"方案 —— "所以我可以先用 mock 数据把整条链路跑通，接真实系统时只改数据访问层。"

---

### B3. MCP server 挂了怎么办？

**一句话**：降级运行，缺哪路证据就少哪路，不让整个应用起不来。

**展开**
> "`init_mcp_tools` 里每个 server 单独 try/except，失败的记录错误、工具列表为空，其他 server 照常加载。真实系统里日志系统在维护，不该让整个诊断平台不可用。
>
> 另外我区分了 liveness 和 readiness：`/healthz` 只看进程活着，MCP 挂了不重启 API（重启也没用）；`/readyz` 会实际探 Postgres、Redis、MCP，任一不可用就返回 false，让负载均衡摘流量。"

**代码位置**：`app/agent/mcp_client.py` 的 `init_mcp_tools`、`app/main.py` 的 `healthz` / `readyz`

## C. LangGraph 类（提问最密集）

### C1. LangGraph 的 State 和 reducer 是什么？你为什么要用 reducer？

**一句话**：State 是图的共享状态，reducer 决定"同一个字段被多个节点同时写时怎么合并"。

**展开**
> "默认行为是**覆盖**。但我的图有并行分支：`Send` 起 N 个 `collect_evidence` 分支，每个返回一条证据。如果用默认覆盖，最后只剩一条。
>
> 所以 `evidence` 用 `operator.add` 做列表拼接。`errors` 同理。
>
> `usage` 比较特殊，token 是**数字求和**不是列表拼接，所以我写了个自定义 reducer `merge_usage`。三种 reducer 对应三种合并语义。"

**代码位置**：`app/agent/state.py`

**加分补充**：*"有 reducer 的字段必须在图入口显式给初始值，否则并行分支第一次写时没有左值会报错。"* —— 这是行家才知道的细节。

---

### C2. `Send` 是怎么实现并行的？为什么能加速？

**一句话**：`Send` 从条件边返回一个列表，LangGraph 为每个元素起一个并行分支，全部完成后才走下一步。

**展开**
> "`dispatch_evidence` 是个条件边函数，它返回 `[Send("collect_evidence", {...}) for req in requests]`。LangGraph 看到列表就并行起 N 个 `collect_evidence` 实例。
>
> 加速的原因：查日志 2 秒、查指标 2 秒、查变更 1 秒、查历史 1 秒，串行 6 秒，并行只需要最慢的那个 —— 2 秒。**实测采集阶段从 8 秒降到 2 秒。**
>
> fan-in 靠 `add_edge("collect_evidence", "synthesize")` 的屏障语义：LangGraph 会等所有并行分支完成才跑 `synthesize`，所以 `synthesize` 能看到全部证据。"

**代码位置**：`app/agent/nodes/investigation.py` 的 `dispatch_evidence`、`app/agent/graph.py`

**加分补充（Send 的三个坑）**
| 坑 | 说明 |
|---|---|
| `Send` 只能从条件边返回 | 从普通节点的返回值里给不生效，会静默不并行 |
| `Send` 的入参是**局部 state** | `collect` 节点里访问 `state["hypotheses"]` 会 KeyError |
| 目标节点名必须逐字匹配 | 拼错会走成单分支，不报错 |

### C3. 你怎么保证 Agent 不死循环、不烧光 token？

**一句话**：三重止损 —— 轮次上限、知道缺什么才回环、根因 unknown 不处置。

**展开**
> "回环条件是三个条件的**与**：置信度低于阈值、轮次没到上限（3 轮）、并且模型明确说出缺什么信息。
>
> 第三条最关键。如果置信度低但 `missing_info` 是空的，说明模型自己都不知道该查什么，再查一轮就是瞎烧 token。所以我要求它在结构化输出里显式填写'还缺什么'，填不出来就不回环，直接转人工。
>
> 另外我在四个位置设了硬闸门：调查轮次上限、单轮最多 6 条请求、工具返回截断（日志行 500 字符、证据 20KB）、指标降采样到 60 个点。全部在代码里，不靠 prompt 说'请节约'。"

**代码位置**：`app/agent/nodes/routing.py` 的 `route_after_synthesis`、`app/config.py`

---

### C4. checkpointer 是什么？为什么必须用它？

**一句话**：checkpointer 按 `thread_id` 把图的每一步状态存下来，支持断点续跑和人在环。

**展开**
> "两个必要性：
>
> 一是**人在环**。`interrupt()` 靠 checkpointer 记录'我停在哪一步'，没配 checkpointer 直接报错。值班人可能 2 小时后才回来审批，中间进程可能重启，状态必须在。
>
> 二是**长流程跨进程**。我的诊断在 ARQ worker 里跑，worker 扩容/重启都是常态。图状态在 Postgres 里，所以任何一个 worker 实例都能接着跑。
>
> 演示时我会把 worker kill 掉，然后审批 —— 图照样从 checkpoint 恢复继续执行。"

**代码位置**：`app/main.py` 的 lifespan、`workers/diagnosis_worker.py` 的 `startup`

**加分补充（必须会的对比）**
> "**checkpointer 和 store 不是一回事。** checkpointer 是图的**内部状态**，按 `thread_id` 存，回答'我在哪'；store 是跨 thread 的**长期记忆**，按 namespace/key 存，回答'我记得什么'。我这个项目里历史故障经验是自己建 `incident_knowledge` 表实现的，因为我要用 pgvector 做相似度检索，LangGraph Store 的检索能力不够。"

### C5. `interrupt()` 的原理是什么？有什么坑？

**一句话**：它抛出一个中断让图暂停，状态存进 checkpointer；resume 时**节点从头重跑**。

**展开**
> "调 `interrupt(payload)` 时图会停下来，payload 出现在返回值的 `__interrupt__` 里，同时状态落 checkpointer。恢复时用 `graph.ainvoke(Command(resume=value), config)`，`value` 就是 `interrupt()` 的返回值。
>
> **最大的坑是：`interrupt()` 所在节点在 resume 时会从头重新执行。** 所以 interrupt 之前的代码会跑两次。我最初把'创建审批记录'写在 interrupt 前面，resume 时插了两行，后来改成幂等 upsert —— 先查有没有，有就复位状态而不是新插。
>
> 第二个坑是 `thread_id` 必须稳定。我一开始想过用随机 uuid，那样 resume 就找不到 checkpoint 了。所以用 `incident-{id}` 这个业务键。"

**代码位置**：`app/agent/nodes/action.py` 的 `request_approval_node`

**加分补充**：*"还有个成本坑：如果 interrupt 之前已经烧了 3 万 token 然后审批被驳回，这些 token 就白烧了。所以 propose_action 我做了规则优先 —— runbook 按根因标签精确匹配命中时不调 LLM，直接填参数模板。"*

### C6. 你的图有多少节点？为什么这么切？

**一句话**：11 个节点，按"职责单一 + 有独立副作用 + 可单独测试"来切。

**展开**
> "ingest（归一化去重）、triage（判要不要查）、plan_investigation（决定查什么）、collect_evidence（执行采集，并行实例）、synthesize（综合根因）、propose_action（生成方案）、request_approval（中断点）、execute_action（幂等执行）、verify（验证恢复）、escalate（转人工）、report（收尾入库）。
>
> 切分的三条原则：**一是每个节点只做一件事**，比如 triage 只判断不采集；**二是副作用独立成节点**，所以 `request_approval` 和 `execute_action` 分开，因为前者会被重跑；**三是可单独测**，我可以 mock 掉 MCP 只测 synthesize 的推理质量。
>
> 特别说一下 `verify` 单独成节点：因为'动作执行成功'不等于'故障恢复'。前者是平台 API 返回 200，后者要指标回落到基线。这两个概念必须分开，否则会误判成已恢复。"

**代码位置**：`app/agent/graph.py`

---

### C7. 图的执行顺序怎么控制的？

**一句话**：普通边定主干，条件边做分支，条件边的路由函数返回值映射到节点名。

**展开**
> "我用 `add_conditional_edges(源节点, 路由函数, {返回值: 目标节点})`。路由函数是纯函数，输入 State 输出字符串，可读、可改、可以打日志。
>
> 比如 `route_after_synthesis` 返回 `plan_investigation` / `propose_action` / `escalate` 三选一，对应三种结局。路由逻辑是显式的代码，不是藏在模型内部的判断 —— 这是 LangGraph 相对'while 循环里让模型决定'的核心优势：**流程可读、可测、可改**。"

**加分补充**：*"我还可以画图验证：`graph.get_graph().draw_mermaid()` 能输出结构图，和设计文档对比就知道有没有接错边。"*

## D. 幂等与安全类

### D1. 你怎么保证执行不会重复？

**一句话**：三层防线，对应三种重复场景。

**展开**
| 层 | 机制 | 防的是什么 |
|---|---|---|
| 1 | 图状态检查 | 同一个人重复点审批 —— 状态不是 `awaiting_approval` 就拒绝 |
| 2 | Redis 分布式锁 | 两个 worker 同时拿到任务 |
| 3 | 数据库唯一索引 + server 侧短路 | 调用超时后重试，**而调用方自己也不知道上次成没成** |

> "第三层是关键。前两层都在调用方，但超时重试这个场景调用方是不知道结果的，所以必须在**被调用方**（executor MCP server）保证幂等：幂等键 = `plan_id + action + target + params` 的稳定哈希，server 收到后先查 `executions` 表，已成功就原样返回首次结果，不重复执行。
>
> 而且我用的是'先查再插 + 唯一索引兜底'：先查是性能优化（正常路径少一次异常），唯一索引是正确性保证（并发竞态下 `IntegrityError` 兜底）。**两个都要，只有唯一索引是保证。**"

**代码位置**：`app/db/repo.py` 的 `claim_execution`、`mcp_servers/executor_server.py` 的 `apply_action`、`app/agent/nodes/action.py`

**加分补充**：*"演示时我会主动重复点一次审批，让面试官看到系统返回 409 拒绝。"*

---

### D2. 分布式锁释放为什么要用 Lua 脚本？

**一句话**：因为"检查是不是自己的锁 + 删除"这两步必须原子，否则会删掉别人的锁。

**展开**
> "场景：进程 A 拿到锁，TTL 3 分钟。A 卡住了 3 分钟，锁自动过期。进程 B 拿到锁。这时 A 醒过来执行释放，如果先 `GET` 判断（发现是自己的 token？不，此时 key 已经是 B 的 token 了），简单实现可能直接 `DEL`，就把 B 的锁删了。
>
> 用 Lua 脚本把'比较 token 相等才 DEL'合成一个原子操作，Redis 单线程执行脚本，中间不会被插入。这就是正确做法。"

**代码位置**：`app/services/dedup.py` 的 `action_lock.__aexit__`

---

### D3. 你怎么防止 AI 乱改生产环境？

**一句话**：诊断和执行是两条权限通道，而且约束写在代码里不在 prompt 里。

**展开**
> "四道门：
>
> 1. **工具分组**：`readonly_tools()` 只返回日志/指标/CMDB 工具，`execute` 节点才拿 executor 的工具。诊断阶段模型根本看不到执行工具。
> 2. **动作白名单**：executor 里有 `ACTION_CATALOG`，不在表里的动作直接抛错。
> 3. **审批强绑定**：HIGH / CRITICAL 风险动作要求 `approval_id` 非空 —— executor 不接受'我口头批准了'，审批记录在库里可审计。
> 4. **根因未知不处置**：`root_cause_tags` 是 `unknown` 时条件路由直接走转人工，不生成处置方案。
>
> 关键点是这些**全在代码里**。prompt 里写'危险操作要谨慎'是不可靠的 —— 模型可能被注入绕过。"

**代码位置**：`mcp_servers/executor_server.py`、`app/agent/mcp_client.py`、`app/agent/nodes/routing.py`

---

### D4. 你怎么做审计？

**一句话**：`audit_logs` 表记录每个状态变更，区分人和 agent。

**展开**
> "actor 字段区分 `agent` / `user:alice` / `system`，`actor_type` 区分 agent / human / system。每次审批、执行、转人工都写一条，带 detail JSON。
>
> 比如审批记录会带 risk_level 和 action —— 因为事后追责不只要知道'谁批了'，还要知道'批了什么风险级别的什么动作'。
>
> 演示时打开审计页面能看到完整链：agent 调查 → human 批准 → agent 执行 → agent 验证。"

## E. 数据库与后端类

### E1. 为什么用 pgvector 而不是 Chroma？

**一句话**：历史故障检索要和业务数据在同一个事务里，而且数据量没到需要专用向量库。

**展开**
> "两个理由：
>
> 一是**一致性**。'找到相似历史故障'和'写入本次诊断结论'可以放在同一个事务里原子提交。用 Chroma 就多一个存储、多一次一致性风险 —— 比如诊断写成功了但向量写失败了。
>
> 二是**规模**。我只有几千条历史故障，pgvector 的 HNSW 索引完全够，甚至不建索引全表扫也就几十毫秒。**引入专用向量库应该是因为规模或功能需要，不是因为'它更专业'。**"

**代码位置**：`app/db/models.py` 的 `IncidentKnowledge`、`app/services/embedding.py`

**加分补充**：*"索引选择上我用了 HNSW 而不是 IVFFlat，因为历史故障是读多写少 —— HNSW 查询快、召回高，代价是构建慢和内存占用大，这个 tradeoff 在我这个场景是划算的。"*

---

### E2. 为什么用 ARQ 而不是 Celery？

**一句话**：ARQ 原生 async，和 FastAPI / LangGraph 的 async 链路一致。

**展开**
> "诊断任务本身是 async IO 密集的 —— 主要时间花在等 LLM 和等 MCP 工具上。Celery 是同步 worker 模型，要用 async 得在事件循环里套线程池，很别扭。ARQ 基于 asyncio，prefork 之外还支持协程并发，`max_jobs` 直接就是协程并发数。
>
> 另外 ARQ 的 `_job_id` 有去重语义，我正好用它做第三道告警去重。"

**加分补充（说出了踩的坑）**
> "但它有个坑：`_job_id` 相同会被静默去重。我一开始 diagnosis 和 resume 用了同样格式的 id，结果**审批通过后什么都不发生** —— 排查半天才发现 resume 任务被当重复任务丢掉了。后来改成 `resume:{id}:{approval_id}`。"

---

### E3. 你的并发上限怎么定的？

**一句话**：worker `max_jobs=5`，是被下游资源约束反推出来的，不是拍脑袋。

**展开**
> "单个诊断平均调 4~6 次 LLM、8~12 次 MCP 工具，端到端 20~40 秒。并发 5 意味着峰值 5 个诊断同时跑：
> - Postgres 连接池我配了 10 + 20 overflow，够
> - LLM 的 rate limit 是最可能先炸的，5 个并发下 QPS 大约 1，安全
>
> 如果设成 50，Postgres 连接和 LLM rate limit 会先崩。所以这个数字是**从下游容量倒推**的，不是随便写的。"

**代码位置**：`workers/diagnosis_worker.py` 的 `WorkerSettings`、`app/db/base.py` 的 `create_async_engine`

---

### E4. SSE 长连接你怎么管理资源？

**一句话**：每次轮询开新 session，绝不让长连接持有数据库连接。

**展开**
> "一个 SSE 连接可能挂 10 分钟。如果全程持有数据库连接，5 个审批台同时打开就能把我 10 个连接的池子耗尽。
>
> 所以 `_collect_timeline` 每次轮询都 `async with SessionLocal()` 开一个新的、用完就还。**长连接不能持有短生命周期资源** —— 这是基本原则。
>
> 另外 SSE 我设了最多推 300 次（约 10 分钟）就结束，防止前端忘了关导致连接泄漏。"

**代码位置**：`app/api/incidents.py` 的 `stream_incident` / `_collect_timeline`

---

### E5. `expire_on_commit=False` 是干什么的？

**一句话**：提交后对象属性不失效，避免 async 上下文里报 `MissingGreenlet`。

**展开**
> "SQLAlchemy 默认 `expire_on_commit=True`：commit 后对象的所有属性被标记为过期，下次访问会触发一次新的查询去刷新。
>
> 在同步代码里这没问题。但在 async 里，属性访问 `incident.id` 是同步的，而刷新查询是异步的 —— 同步上下文里触发异步 IO，就报 `MissingGreenlet`。这是 async SQLAlchemy 最经典的坑。
>
> 设成 False 就不会过期，代价是可能读到稍旧的数据。在'提交后立刻用'的场景里这个代价可以接受。"

**代码位置**：`app/db/base.py` 的 `async_sessionmaker`

---

### E6. `pool_pre_ping` 为什么需要？

**一句话**：防止从连接池拿到已被服务端静默断开的死连接。

**展开**
> "Postgres 或中间的负载均衡/防火墙会掐掉空闲太久的连接，但连接池不知道，以为它还活着。下次拿出来用就报错。
>
> `pool_pre_ping=True` 会在取连接时先发一个轻量探测，发现死了就丢弃重建。代价是每次取连接多一个 RTT，但比偶发的连接错误划算。
>
> 配合 `pool_recycle=1800`：主动在 30 分钟时回收连接，比被动等它被断开更可控。"

**代码位置**：`app/db/base.py` 的 `create_async_engine`

---

### E7. 你的迁移出问题怎么办？

**一句话**：Alembic 版本化，可 downgrade，上线前演练回滚。

**展开**
> "每个迁移都有 `upgrade` 和 `downgrade`。我在验收清单里专门有一条'`downgrade -1 && upgrade head` 来回跑通'，就是为了证明回滚路径是通的。
>
> 另外 `vector` 扩展这种 Alembic 不会自动生成的，我在迁移里手写 `op.execute("CREATE EXTENSION IF NOT EXISTS vector")`。**autogenerate 生成的迁移必须人工 review** —— 它经常漏掉扩展、部分索引、CHECK 约束。"

## F. 可观测与评估类

### F1. 你怎么知道效果好不好？

**一句话**：三层 —— 链路追踪看开销，业务指标看运营，评估集看质量。

**展开**
> "**链路层**用 Langfuse 看单次诊断里每个节点、每次 LLM 调用的耗时和 token。
>
> **业务层**把 token 和成本写进 incidents 表做聚合，算自动恢复率、转人工率、平均 MTTR、单次成本、平均调查轮次。
>
> **质量层**是唯一需要评估集的：我做了 5 个故障场景的评估集，每个场景有 ground truth（期望的服务、根因标签、期望动作），`run_eval` 自动回放并记录根因准确率。"

**代码位置**：`app/obs/tracing.py`、`app/api/metrics.py`、`eval/run_eval.py`

---

### F2. 你的准确率怎么算的？为什么不用文本匹配？

**一句话**：用根因标签集合求交集，不用字符串精确匹配。

**展开**
> "我第一版用字符串精确匹配，准确率永远是 0 —— 因为模型的根因表述每次都不一样，'JVM 堆内存泄漏'和'内存持续增长导致 GC 频繁'说的是同一件事。
>
> 改成根因标签匹配：我在结构化输出里限定 tags 必须从固定枚举里选（memory_leak / bad_release / db_deadlock / cpu_saturation / cache_miss_storm...），评估时判断预测标签和期望标签**有交集即算对**。
>
> 而且我给每个案例跑 3 次做多数投票。LLM 输出有随机性，单次结果可能就是运气好 —— 报告里我给的是多数结果，不是单次点估计。"

---

### F3. 你怎么验证你的评估是有效的？

**一句话**：把 prompt 里最关键的一条删掉，准确率应该下降。

**展开**
> "评估集如果对改动不敏感，说明它太简单或者指标设计有问题。所以我的验收清单里有这么一条：**故意删掉 prompt 里'先看变更'这条方法论，重跑评估**。如果准确率不变，说明评估集无效。
>
> 我实测是从 XX% 掉到 XX% —— 说明评估真的能区分好坏，不是走过场。
>
> 另外我还验证了没有评估泄漏：mock 告警里带了个 `scenario` 字段直接标明答案，我在 ingest 节点里显式剥离了它，只存进 `alerts.raw`，绝不进 prompt。**验证方法是把模型换个随便答的版本，准确率应该掉到 20% 左右（5 个场景里的 1/5）。**"

**代码位置**：`app/agent/nodes/ingest.py` 的 `_sanitize_labels`、`eval/run_eval.py`

**加分补充**：这个问题是"高级候选人过滤器"。能主动讲评估泄漏的候选人极少。

---

### F4. 你做过什么性能优化？

**一句话**：三个优化，都有实测数字。

**展开**
| 优化 | 做法 | 效果 |
|---|---|---|
| **并行证据采集** | `Send` fan-out 替代串行 | 采集阶段 8s → 2s |
| **规则优先于 LLM** | runbook 按 tags 精确匹配命中时直接填参数模板，不调 LLM | `propose_action` 的 LLM 调用从 100% 降到 30% |
| **小模型分流** | triage 和 propose_action 用 cheap 模型 | 这两处占调用总数 40%，总成本降约 25% |

**加分补充（区分"系统慢"和"流程慢"）**
> "另外我把延迟做了分解，其中 **`approval_wait_ms`（等人审批的时间）单独统计**，不混进 Agent 自身耗时。因为值班人可能睡了 20 分钟，把那个算进 Agent 延迟里，优化效果就完全看不出来了。**分得清'系统慢'和'流程慢'本身就是指标设计的一部分。**"

---

### F5. 成本怎么控制的？

**一句话**：四个硬闸门 + 三个 prompt 优化。

**闸门（都在代码里）**
| 闸门 | 值 | 作用 |
|---|---|---|
| `max_investigation_rounds` | 3 | 回环上限 |
| `max_evidence_per_round` | 6 | 单轮并行分支上限 |
| 日志行截断 | 500 字符 | 防止单条超长堆栈吃光上下文 |
| 证据 payload 上限 | 20000 字符 | 防单行过大 |
| 指标降采样 | ≤ 60 个点 | 时序数据抽样 |

**优化**
> "工具设计上我做了取舍：不提供'拉原始日志'这种工具让模型自己读，而是提供 `top_error_patterns` 这种**聚合后**的工具，把聚类逻辑放在工具侧用代码做，只把结论喂给模型。**工具要有洞察，不要当管道** —— 这是最大的一笔成本节省。"

---

### F6. 你怎么知道 Agent 在哪一步慢？

**一句话**：`/metrics/nodes` 按 MCP 工具统计调用次数和平均耗时。

**展开**
> "我有一张 `evidence` 表记录了每次工具调用，配合 `/metrics/nodes` 接口按工具聚合，能看到调用次数、成功率、平均耗时、最大耗时。
>
> 实测下来 `top_error_patterns` 平均 800ms 是瓶颈 —— 因为它在 2000 条日志上做正则模板聚类。这就是我下一步优化的方向：加缓存或者改成增量聚类。
>
> 这个是 Langfuse 之外的补充：Langfuse 看单次 trace，这个接口看全局分布。"

## G. 反问与压力测试类

### G1. 这个项目有多少是自己写的？

**诚实答法**

**为什么这样答**：面试官欣赏"知道参考了什么、借鉴到什么程度"的候选人，讨厌"全是我原创"（不可信）和"我抄的"（没思考）。

### G2. 如果让你上生产，你会补什么？

**展开（按优先级）**
> "1. **真实数据源接入**：把 4 个 mock server 换成真 Loki / Prometheus / CMDB / K8s API。数据访问层已经隔离在 `store.py` 里，改动可控。
> 2. **鉴权与多租户**：现在 webhook 只有一个共享 token。生产要按团队隔离，不同服务的告警只能看自己的故障。
> 3. **审批通知**：现在审批靠值班人主动看审批台。生产要接 Slack / 飞书 / 电话告警。
> 4. **成本预算与熔断**：单次诊断超过预算（比如 $0.1）直接中止转人工。
> 5. **幂等的更严格保证**：executor 现在查 `executions` 表，生产要换成"调用被调用方的幂等接口 + 对账"。
> 6. **评估集扩充**：5 个场景太少。要按故障类型 × 服务维度扩到 30+ 个，并且定期用线上真实故障回流。"

**为什么这样答**：展示你知道"Demo 和生产之间差什么"，这是 AI 应用开发岗最看重的能力。

### G3. 为什么用 DeepSeek 不用 GPT/Claude？

**一句话**：成本 + OpenAI 兼容接口，可以随时切换。

**展开**
> "我用的是 OpenAI 兼容接口，所以模型是可替换的 —— 改 `LLM_BASE_URL` 和 `LLM_MODEL` 就行。选 DeepSeek 主要是成本，诊断场景要反复调 LLM，成本敏感。temperature 我设成 0.1，因为诊断要稳定不要创造性。

### G4. 这个项目有什么没做好的？

**必须有一个真实的答案**（说"都挺好"最减分）

> "三个：
>
> 一是**告警关联规则太简单**，现在是'同服务 15 分钟内的告警聚成一个 incident'。真实场景要按拓扑关联、按根因指纹聚合，复杂得多。我把关联逻辑抽成了 `_find_or_create_incident` 一个函数，方便以后替换。
>
> 二是**根因标签没落库**。现在 `hypotheses` 表存了 statement 和 rationale，但没存模型的 tags，评估时要从文本里粗提取关键词。这不对，应该加个 `tags JSONB` 字段直接存。这是我发现的第一版设计缺陷。
>
> 三是**置信度可能不诚实**。我在指标看板里想加一条校准曲线 —— 按置信度分桶看实际准确率。如果置信度 0.9 的样本只有 50% 正确，那我的 `confidence_threshold` 路由依据就不可靠了。这个我还没做完。"

**为什么这样答**：第三个答案是"我知道自己系统的弱点在哪"，比任何自我表扬都有说服力。

---

### G5. 如果不用 LangGraph，你会怎么做？

**一句话**：会做，但会丢掉三样东西。

**展开**
> "用手写状态机 + Redis 存状态也能实现。但会丢掉：
>
> 一是**并行的简洁性**。手写 fan-out/fan-in 要自己管 asyncio.gather、超时、部分失败、结果合并，LangGraph 的 `Send` + reducer 内建了。
>
> 二是**持久化的正确性**。自己存状态很容易漏掉'并行分支中间写入'这种情况，而且版本演进时状态结构变化很难处理。checkpointer 帮我处理了序列化和版本。
>
> 三是**人在环的标准做法**。`interrupt()` + `Command(resume=)` 是经过设计的模式，包括那个'节点重跑'的语义都是有意的 —— 它保证 interrupt 之后的状态总是从 checkpointer 重建，不会有内存态和持久态不一致。自己实现很容易在这点上出错。
>
> 所以不是说不用框架就做不了，而是**框架在这些边界情况上帮我省了踩坑的时间**。"
